## User Story

As the release operator for `claude-i`, I want the first PyPI publish to use a
fresh `0.2.4` release that matches current `main`, so PyPI does not publish the
older `v0.2.3` tag or create a mismatch between package contents and release
metadata.

## Context

The existing `v0.2.3` tag points to `ab84d59`, while current `main` includes
additional validated maintenance:

- STORY-001.10 late Stop-hook `.done` cleanup
- STORY-001.11 Bug 5 final-error UX
- STORY-001.12 GitHub Actions Node 24 hardening and Fedora registry pivot

Because PyPI versions are permanent, publishing `0.2.3` from `main` would make
PyPI contents differ from the `v0.2.3` GitHub tag. Publishing from the old tag
would omit the fixes already validated for the PyPI path. This story bumps the
release to `0.2.4` before the first Trusted Publisher dispatch.

## Acceptance Criteria

- **AC-1:** Runtime package version is `0.2.4` in `pyproject.toml` and
  `src/claude_i/__init__.py`.
- **AC-2:** README install/status surfaces are PyPI-first for `0.2.4`.
- **AC-3:** CHANGELOG documents `0.2.4` and why it exists.
- **AC-4:** PyPI and Homebrew operational guides point future publish/flip
  commands at `v0.2.4` while preserving true current Homebrew formula state.
- **AC-5:** Local validation passes: ruff, mypy, pytest, build, twine, wheel
  and sdist install smoke, `claude-i doctor --json`, and `git diff --check`.
- **AC-6:** PR and post-merge GitHub Actions checks pass before tagging.
- **AC-7:** No PyPI publish is run until the Trusted Publisher is configured and
  the `v0.2.4` tag/release exists.
